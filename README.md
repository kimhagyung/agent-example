### **[LangGraph 소개]**

LangGraph는 매우 가볍고 미니멀한 프레임워크지만, 그만큼 이해가 필요한 핵심 개념들이 존재한다.

* **미니멀리즘:** Built-in 기능이 많지 않아 직접 구현해야 하는 부분이 많지만, 한 번 이해하면 어떤 복잡한 시스템도 설계할 수 있다.
* **높은 자유도:** `crewAI`, `autogen`, `OpenAI SDK`처럼 이미 만들어진 `Agent`나 `Assistant` 클래스를 호출하는 방식이 아니다.
* **직접 설계:** 지시문(Instruction)이나 도구(Tools)를 세팅하는 방식이 아니라, 모든 규칙을 코드로 직접 구현하므로 매우 유연하며 제어권이 개발자에게 있다.
* **코드 중심:** 다른 프레임워크에 비해 작성할 코드는 많아지지만, 그만큼 정교한 워크플로우를 만들 수 있다.

### **[핵심 개념: Graph]**

에이전트 자체가 하나의 거대한 그래프이다. 우리가 흔히 그리는 워크플로우 다이어그램을 코드로 옮겨놓은 것이라고 생각하면 쉽다.

| 구성 요소 | 설명 |
| --- | --- |
| **State (상태)** | 그래프를 통해 흐르는 **데이터** 그 자체. 모든 노드가 공유하고 업데이트할 수 있다. |
| **Node (노드)** | 실제로 **작업이 일어나는 곳**. 파이썬 함수 형태로 정의하며 State를 받고 업데이트된 State를 반환한다. |
| **Edge (엣지)** | 노드와 노드를 연결하는 **화살표**. 데이터의 흐름과 실행 순서를 결정한다. |

#### **그래프 생성 순서**

1. **State 선언:** 그래프 전체에서 사용할 데이터 스키마 정의 (`TypedDict`)
2. **노드 함수 생성:** 각 단계에서 실행할 구체적인 로직 작성
3. **add_node:** 그래프 빌더에 노드 이름과 함수 등록
4. **Edge 추가:** `START` ➡ `Node` ➡ `END` 사이의 흐름 연결
5. **Compile:** 설계를 마치고 실행 가능한 그래프 객체 생성

### **[Multiple Schemas: Divide and Conquer]**

LangGraph에서는 **Input, Output, Private** 세 가지 타입의 스키마를 분리해서 관리할 수 있다.

* **분할 정복(Divide and Conquer):** 내부 연산에 필요한 방대한 데이터(Private)와 사용자에게 보여줄 데이터(Input/Output)를 분리하여 복잡도를 낮춘다.
* **보안 및 캡슐화:** 사용자가 알 필요 없는 내부 상태를 숨기고, 최종적으로 필요한 결과값만 정제해서 반환할 수 있다.
 
### **[Conditional Edges]**

노드에서 다음 노드로 갈 때, 고정된 경로가 아닌 특정 조건에 따라 경로를 결정한다.

* **사용법:** 기존 `graph_builder.add_edge` 대신 `graph_builder.add_conditional_edges`를 사용한다.
* **루팅 함수:** 상태(State)를 확인하여 다음 이동할 노드의 이름을 반환하는 함수를 작성하여 연결한다.

### **[Send API]**

`Send` 클래스는 커스텀 상태(Custom State)를 가진 노드를 **동적으로 호출(Invoke)** 할 수 있게 해준다.

* **필요성:** 작업을 몇 번 반복해야 할지 미리 알 수 없는 경우(예: 처리해야 할 파일 개수가 가변적일 때) 유용하다.
* **병렬 처리:** 여러 노드를 동시에 실행하고 싶을 때 `Send`를 사용하면 모든 노드가 병렬로 실행될 수 있다.
* **특징:** 기본적으로 노드는 한 사이클만 돌지만, `Send`를 쓰면 노드를 미리 복사해두지 않고도 원하는 만큼 동적으로 노드를 생성해 실행하는 것과 같은 효과를 준다.

---

### **[Command]**

노드 사이의 **Handoff(넘겨주기)** 개념과 유사하며, 그래프의 흐름을 아주 유연하게 제어한다.

* **핵심 기능:** 다른 노드로 이동(`goto`)함과 동시에 상태(`update`)를 업데이트하고 싶을 때 사용한다.
* **점프 기능:** 기존의 엣지 연결을 무시하고 그래프 내의 어떤 노드로든 즉시 점프할 수 있다.

**💡 Command vs Conditional Edge: 언제 쓸까?**
| 비교 항목 | Command 사용 | Conditional Edge 사용 |
| :--- | :--- | :--- |
| **상태 업데이트** | 이동과 동시에 State 업데이트 가능 | 이동 로직만 담당 |
| **유연성** | 노드 내부 로직에서 즉시 결정 (Jump) | 미리 정의된 경로(Edge) 내에서 결정 |
| **추천 상황** | **전달(Transfer) + 업데이트**가 동시 필요할 때 | 단순히 경로 분기만 필요할 때 |

### **[Tool Nodes]**

챗봇에 **Function Calling**을 추가하여 단순 챗봇을 '에이전트'로 업그레이드하는 과정이다.

* **작동 원리:** `conditional_edge`를 사용하여 LLM의 응답을 확인한다.
* **워크플로우:** 1. LLM 응답에 `tool_calls`가 포함되어 있다면 `tools_node`로 이동.
2. 도구 실행 결과를 받아서 다시 챗봇(LLM)으로 돌아감.
3. LLM이 도구 결과를 바탕으로 최종 답변을 생성하면 대화 종료.
* 결국, 도구들을 실행하고 관리하는 전용 노드 역할을 한다.

### **[Memory & Checkpointers]**

LangGraph의 메모리는 단순히 대화 내용을 저장하는 것을 넘어선다.

* **Checkpointers:** 상태(State)뿐만 아니라 **상태가 변해온 이력(History)** 전체를 기록한다.
* **가시성:** 그래프가 어떤 노드들을 거쳐왔는지 완벽하게 추적할 수 있다.
* **분기(Forking):** 과거의 특정 시점으로 돌아가서 메시지를 수정한 뒤, 다른 방향으로 대화를 이어나가는 것이 가능하다.

---

### **[Human-in-the-loop]**

에이전트의 실행을 중간에 멈추고 **사람의 피드백이나 승인**을 받는 기능이다.

* **중단점(Breakpoints):** 그래프 실행을 일시 중단하고 사용자가 보고서를 승인, 수정, 혹은 거부할 수 있게 한다.
* **안전성:** 결제나 데이터 삭제처럼 파괴적이거나 민감한 도구를 사용할 때, 에이전트가 독단적으로 행동하지 않도록 승인 절차를 강제할 수 있어 프로덕션 환경에서 매우 중요하다.

---

### **[Time Travel]**

체크포인터에 저장된 데이터를 바탕으로 대화의 과거 시점으로 돌아가는 기능이다.

* **Conversation Forking:** 이전 체크포인트로 돌아가서 상태를 수정한 뒤 다시 시작하면, 대화의 **대안 경로(Alternative Path)**를 만들 수 있다.
* **디버깅:** 에이전트가 잘못된 답변을 했을 때 그 직전 상태로 돌아가 데이터를 수정하고 다시 실행해 볼 수 있다.
